# ADR 0001: Persistir e consultar o histórico de rastreabilidade em um repositório relacional

- **Status:** Proposto
- **Data:** 10/11/2026

## Contexto

O AutoFlow Monitor precisa permitir que o Analista de Qualidade consulte o histórico de uma peça, relacionando os ciclos de usinagem aos testes de estanqueidade realizados, incluindo os resultados dos retestes.

A consulta exige que os registros possam ser recuperados por identificador da peça e apresentados em uma sequência temporal coerente. Também é importante preservar cada execução de teste individualmente: um reteste não deve apagar nem sobrescrever o resultado do teste anterior. A relação entre peça, ciclo e teste precisa ser mantida para apoiar a rastreabilidade.

## Decisão

Adotar, como proposta para a arquitetura, um banco de dados relacional PostgreSQL para persistir os dados de peças, ciclos de usinagem e testes de estanqueidade.

A API de Rastreabilidade será responsável por:
- receber o identificador da peça;
- validar a solicitação e localizar a peça;
- consultar os ciclos de usinagem e os testes de estanqueidade associados;
- recuperar retestes como registros independentes;
- consolidar os dados em uma estrutura de histórico ordenada cronologicamente;
- retornar à interface um DTO de consulta, sem alterar os registros de produção.

A interface web apresentará os eventos em uma linha do tempo, diferenciando ciclos, testes iniciais e retestes.

## Consequências

### Positivas
- Consultas por identificador da peça podem ser organizadas por relacionamentos e índices.
- A estrutura relacional favorece a integridade das associações entre peça, ciclo e teste.
- Cada reteste permanece preservado como evento independente, permitindo consultar a sequência de resultados.
- A separação entre interface, API e banco de dados facilita manutenção e evolução.

### Negativas
- O modelo de dados precisa definir corretamente as chaves e relacionamentos entre peças, ciclos e testes.
- Consultas que consolidam muitos eventos podem exigir índices e otimização.
- A equipe precisa cuidar da consistência temporal e da associação dos registros à peça correta.

### Riscos e pontos a validar
- Confirmar no documento de requisitos como RF06 e RF13 definem a associação entre peça, ciclo e teste.
- Definir o identificador oficial da peça e a regra para associar testes realizados novamente.
- Definir como o sistema deve exibir registros sem vínculo confiável com uma peça.
- A tecnologia PostgreSQL é uma escolha proposta neste ADR e deve ser validada com as restrições do projeto.
